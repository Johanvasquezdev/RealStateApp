Objetivo general  
Desarrollar una aplicación web para la gestión de propiedades inmobiliarias, 
utilizando ASP.NET Core MVC 9, que permita administrar de manera integral el 
registro, consulta, publicación y seguimiento de propiedades disponibles para venta o 
alquiler. El sistema debe permitir que los usuarios visitantes consulten propiedades 
disponibles, apliquen filtros de búsqueda, visualicen el detalle completo de cada 
propiedad y revisen la información de los agentes inmobiliarios asociados. 
Además, la aplicación debe permitir que los clientes registrados puedan marcar 
propiedades como favoritas, comunicarse con los agentes mediante un módulo de 
mensajería y realizar ofertas sobre propiedades disponibles. De igual forma, los 
agentes inmobiliarios deben poder gestionar sus propiedades, responder mensajes, 
revisar ofertas recibidas y actualizar el estado de una propiedad cuando una oferta 
sea aceptada. La plataforma también debe permitir que los administradores 
gestionen los usuarios del sistema, los agentes inmobiliarios, los desarrolladores, los 
tipos de propiedades, los tipos de ventas y las mejoras disponibles para las 
propiedades. 
Finalmente, el sistema debe incluir una API protegida mediante autenticación JWT, 
que permita consultar y administrar información clave de la aplicación según los roles 
autorizados, garantizando el control de acceso, la seguridad de los datos y la correcta 
separación de responsabilidades entre la aplicación web y los servicios expuestos. 
Funcionalidades generales  
Home  
El sistema debe mostrar una pantalla inicial pública donde cualquier usuario, sin 
necesidad de iniciar sesión, pueda consultar las propiedades inmobiliarias 
disponibles registradas en la aplicación. 
Esta pantalla debe funcionar como el punto principal de acceso para visualizar 
propiedades, realizar búsquedas, aplicar filtros y consultar el detalle completo de 
una propiedad específica.​

Validaciones de la búsqueda por código 
Al realizar una búsqueda por código, el sistema debe cumplir las siguientes 
validaciones: 
●​ Si el campo está vacío, el sistema debe mantener el listado general de 
propiedades disponibles. 
●​ Si el código ingresado existe y pertenece a una propiedad disponible, el 
sistema debe mostrar dicha propiedad. 
●​ Si el código ingresado no existe o pertenece a una propiedad que no está 
disponible, el sistema debe mostrar un mensaje indicando que no se 
encontraron propiedades con ese código. 
Mensaje sugerido: 
“No se encontró ninguna propiedad disponible con el código ingresado.”

●​ El precio máximo no puede ser menor que cero.

●​ Todos los filtros deben poder aplicarse al mismo tiempo. 
●​ El sistema solo debe mostrar propiedades que cumplan con todos los filtros 
seleccionados. 
Si los filtros aplicados no devuelven resultados, el sistema debe mostrar un 
mensaje como: 
“No se encontraron propiedades disponibles con los filtros 
seleccionados.”

Reglas adicionales del Home 
El módulo Home debe cumplir las siguientes reglas: 
●​ La pantalla inicial debe ser pública y no debe requerir inicio de sesión. 
●​ Sólo deben mostrarse propiedades en estado Disponible. 
●​ Las propiedades vendidas no deben aparecer en el Home público. 
●​ Las propiedades deben listarse desde la más reciente hasta la más antigua. 
●​ El usuario debe poder buscar por código de propiedad. 
●​ El usuario debe poder aplicar filtros por tipo de propiedad, rango de precio, 
cantidad de habitaciones y cantidad de baños. 
●​ Los filtros deben poder combinarse entre sí. 
●​ Al seleccionar una propiedad, el sistema debe mostrar su detalle completo. 
●​ La pantalla de detalle solo debe estar disponible para propiedades 
existentes y disponibles. 
●​ Si una propiedad no existe o no está disponible, el sistema debe mostrar un 
mensaje indicando que la propiedad no pudo ser encontrada. 
Mensaje sugerido: 
“La propiedad solicitada no existe o no se encuentra 
disponible.”

Representa la imagen de perfil del usuario. Esta imagen será utilizada para mostrar

●​ .jpeg

●​ El nombre es requerido. 
●​ El apellido es requerido. 
 
●​ El teléfono es requerido. 
●​ La foto de usuario es requerida. 
●​ El nombre de usuario es requerido. 
●​ El nombre de usuario no debe estar registrado previamente. 
●​ El correo electrónico es requerido. 
●​ El correo electrónico debe tener un formato válido. 
●​ El correo electrónico no debe estar registrado previamente. 
●​ La contraseña es requerida. 
●​ La confirmación de contraseña es requerida. 
●​ La contraseña y la confirmación de contraseña deben coincidir. 
●​ El tipo de usuario es requerido. 
●​ El tipo de usuario seleccionado debe ser Cliente o Agente. 
●​ El archivo cargado como foto debe ser una imagen válida. 
●​ El archivo cargado debe tener un formato permitido. 
Si el usuario intenta registrarse sin completar algún campo requerido, el sistema 
debe mostrar un mensaje como: 
“Debe completar todos los campos requeridos.” 
Si el correo electrónico ingresado no tiene un formato válido, el sistema debe 
mostrar un mensaje como: 
“Debe ingresar un correo electrónico válido.” 
Si el correo electrónico ya está registrado, el sistema debe mostrar un mensaje 
como: 
“Ya existe un usuario registrado con este correo electrónico.” 
Si el nombre de usuario ya está registrado, el sistema debe mostrar un mensaje 
como: 
“Ya existe un usuario registrado con este nombre de usuario.” 
Si la contraseña y la confirmación de contraseña no coinciden, el sistema debe 
mostrar un mensaje como: 
“La contraseña y la confirmación de contraseña no coinciden.” 
Si el archivo cargado como foto no es una imagen válida, el sistema debe mostrar 
 
un mensaje como: 
“El archivo seleccionado no tiene un formato de imagen válido.” 
Flujo de registro para clientes 
Si el usuario selecciona el tipo de usuario Cliente, el sistema debe crear la cuenta 
con rol Cliente y estado Inactivo. 
Luego de crear la cuenta, el sistema debe enviar un correo electrónico al cliente con 
las instrucciones necesarias para activar su usuario. 
El correo debe enviarse a la dirección registrada en el campo Correo electrónico. 
El mensaje del correo puede tener un contenido como el siguiente: 
Asunto: Activación de cuenta en RealEstateApp 
Hola [Nombre del cliente], 
Su cuenta ha sido registrada correctamente en RealEstateApp. 
Para activar su usuario y poder iniciar sesión, utilice el siguiente enlace o código de 
activación: 
[ENLACE O CÓDIGO DE ACTIVACIÓN] 
Si usted no realizó este registro, puede ignorar este mensaje. 
Después de enviar el correo de activación, el sistema debe redirigir al usuario a la 
pantalla de inicio de sesión y mostrar un mensaje como: 
“Su cuenta ha sido creada correctamente. Revise su correo electrónico 
para activar su usuario.” 
El cliente no debe poder iniciar sesión hasta que su cuenta haya sido activada 
correctamente. 
Flujo de registro para agentes 
Si el usuario selecciona el tipo de usuario Agente, el sistema debe crear la cuenta 
con rol Agente y estado Inactivo. 
 
En este caso, el sistema no debe enviar correo de activación al agente, debido a que 
la activación de agentes debe ser realizada manualmente por un usuario con rol 
Administrador. 
Después de crear la cuenta del agente, el sistema debe redirigir al usuario a la 
pantalla de inicio de sesión y mostrar un mensaje como: 
“Su cuenta de agente ha sido creada correctamente. Un administrador 
debe activar su usuario antes de que pueda iniciar sesión.” 
El agente no debe poder iniciar sesión hasta que un administrador active su cuenta 
desde el módulo correspondiente. 
Reglas adicionales del registro 
El módulo Únete a la app debe cumplir las siguientes reglas: 
●​ La pantalla de registro debe ser pública y no debe requerir inicio de sesión. 
●​ Desde esta pantalla solo se deben poder registrar usuarios de tipo Cliente o 
Agente. 
●​ Los usuarios registrados desde esta pantalla siempre deben crearse en 
estado Inactivo. 
●​ Los clientes deben activar su cuenta mediante un correo de activación. 
●​ Los agentes deben ser activados manualmente por un administrador. 
●​ Un usuario inactivo no debe poder iniciar sesión. 
●​ El sistema debe impedir registros con correos electrónicos repetidos.

Responder una oferta 
Cuando una oferta se encuentre en estado pendiente, el sistema debe permitir al 
agente responder mediante las acciones Aceptar o Rechazar. 
Si el agente selecciona la opción Rechazar, el sistema debe cambiar el estado de la 
oferta a Rechazada. 
Si el agente selecciona la opción Aceptar, el sistema debe realizar las siguientes 
acciones: 
●​ Cambiar el estado de la oferta seleccionada a Aceptada. 
●​ Cambiar el estado de todas las demás ofertas pendientes de esa propiedad a 
Rechazada, sin importar si pertenecen al mismo cliente o a otros clientes. 
●​ Cambiar el estado de la propiedad a Vendida. 
●​ Impedir que cualquier cliente pueda realizar nuevas ofertas sobre esa 
propiedad. 
Esta operación debe ejecutarse de forma completa para evitar que la propiedad 
 
quede vendida con más de una oferta aceptada. 
Validaciones para responder ofertas 
El sistema debe cumplir las siguientes validaciones antes de permitir que el agente 
responda una oferta: 
●​ El agente debe estar autenticado. 
●​ El usuario autenticado debe tener rol Agente. 
●​ La propiedad debe existir. 
●​ La propiedad debe pertenecer al agente autenticado. 
●​ La oferta debe existir. 
●​ La oferta debe pertenecer a la propiedad seleccionada. 
●​ La oferta debe encontrarse en estado pendiente. 
●​ La propiedad debe estar en estado Disponible para poder aceptar una oferta. 
●​ No debe existir otra oferta aceptada para la misma propiedad. 
Si el agente intenta responder una oferta que ya fue aceptada o rechazada, el 
sistema debe mostrar un mensaje como: 
“Esta oferta ya fue respondida.” 
Si el agente intenta aceptar una oferta de una propiedad vendida, el sistema debe 
mostrar un mensaje como: 
“No se puede aceptar una oferta para una propiedad que ya fue 
vendida.” 
Si la oferta se rechaza correctamente, el sistema debe mostrar un mensaje como: 
“La oferta fue rechazada correctamente.” 
Si la oferta se acepta correctamente, el sistema debe mostrar un mensaje como: 
“La oferta fue aceptada correctamente y la propiedad fue marcada como 
vendida.” 
Reglas adicionales del detalle de propiedad del agente 
El detalle de propiedad del agente debe cumplir las siguientes reglas: 
●​ Solo usuarios autenticados con rol Agente deben acceder a esta pantalla. 
●​ El agente solo debe acceder al detalle de propiedades registradas por él. 
●​ El agente no debe poder gestionar conversaciones ni ofertas de propiedades 
pertenecientes a otros agentes. 
 
●​ El agente debe poder visualizar las conversaciones asociadas a cada 
propiedad. 
●​ El agente debe poder responder mensajes enviados por clientes. 
●​ El agente debe poder visualizar los clientes que han realizado ofertas sobre 
la propiedad. 
●​ El agente debe poder consultar el historial completo de ofertas realizadas 
por cada cliente. 
●​ Solo las ofertas en estado pendiente deben permitir acciones de aceptación 
o rechazo. 
●​ Una propiedad solo puede tener una oferta aceptada. 
●​ Al aceptar una oferta, la propiedad debe cambiar automáticamente a estado 
Vendida. 
●​ Al aceptar una oferta, todas las demás ofertas pendientes de la misma 
propiedad deben cambiar automáticamente a estado Rechazada. 
●​ Una vez que la propiedad esté vendida, no se deben permitir nuevas ofertas. 
●​ Las ofertas rechazadas y aceptadas deben permanecer visibles como 
historial.

El módulo Mi perfil debe cumplir las siguientes reglas: 
●​ Solo usuarios autenticados con rol Agente deben acceder a esta pantalla. 
●​ El agente solo debe poder modificar su propia información. 
●​ El agente no debe poder modificar información de otros usuarios. 
●​ El sistema debe mostrar los datos actuales del agente al cargar el formulario. 
●​ La foto actual debe mostrarse en pantalla antes de guardar cambios. 
●​ La foto solo debe reemplazarse si el agente carga una nueva imagen válida. 
●​ Si el agente presiona Volver atrás, el sistema debe regresar al Home del 
agente sin guardar cambios. 
●​ Si el agente presiona Guardar cambios y las validaciones son correctas, el 
sistema debe actualizar la información del perfil.

al Home del administrador. 
Esta pantalla debe funcionar como el panel principal de administración de la 
aplicación. Desde ella, el administrador podrá acceder a los mantenimientos 
generales del sistema y visualizar indicadores resumidos sobre propiedades y 
usuarios registrados.

Reglas adicionales del Home del administrador 
El Home del administrador debe cumplir las siguientes reglas: 
●​ Solo los usuarios autenticados con rol Administrador debe poder acceder a 
esta pantalla. 
●​ Un usuario con rol Cliente, Agente o Desarrollador no debe poder acceder al 
Home del administrador. 
●​ Si un usuario no autorizado intenta acceder directamente mediante la URL, el 
sistema debe redirigirlo a una pantalla de acceso denegado o a su Home 
correspondiente, según aplique. 
●​ El menú del administrador solo debe mostrar opciones correspondientes a 
funcionalidades administrativas. 
●​ Los indicadores deben mostrar datos actualizados según los registros 
 
existentes en el sistema. 
●​ Las propiedades deben contarse separando las que están en estado 
Disponible y las que están en estado Vendida. 
●​ Los usuarios deben contarse separando los activos e inactivos según su rol. 
●​ Los usuarios con rol Desarrollador pueden ser administrados desde la 
WebApp, aunque su uso principal sea el acceso autorizado a la API.

Esta pantalla debe permitir al administrador visualizar los agentes inmobiliarios del 
sistema, activar o inactivar sus cuentas y eliminar agentes cuando sea necesario.

Activar o inactivar agente 
El sistema debe mostrar una acción para activar o inactivar al agente según su 
estado actual. 
Si el agente se encuentra activo, debe mostrarse una opción para Inactivar. 
Si el agente se encuentra Inactivo, debe mostrarse una opción para Activar. 
Antes de cambiar el estado del agente, el sistema debe mostrar una confirmación. 
Mensaje sugerido para inactivar: 
“¿Está seguro que desea inactivar este agente?” 
Mensaje sugerido para activar: 
“¿Está seguro que desea activar este agente?” 
Si el administrador confirma la acción, el sistema debe actualizar el estado del 
agente y regresar al listado de agentes. 
Si el administrador cancela la acción, el sistema debe permanecer en el listado sin 
realizar cambios. 
Efectos de inactivar un agente 
Cuando un agente sea inactivado, el sistema debe cumplir las siguientes reglas: 
●​ El agente no debe poder iniciar sesión. 
●​ El agente no debe aparecer en el listado público de agentes. 
●​ Las propiedades disponibles del agente no deben mostrarse en las secciones 
públicas de la aplicación. 
●​ El administrador debe poder volver a activar al agente cuando sea necesario. 
Si el agente se inactiva correctamente, el sistema debe mostrar un mensaje como: 
 
“El agente fue inactivado correctamente.” 
Si el agente se activa correctamente, el sistema debe mostrar un mensaje como: 
“El agente fue activado correctamente.” 
Eliminar agente 
Cada agente del listado debe tener una opción para eliminarlo. 
Al presionar el botón Eliminar, el sistema debe redirigir al administrador a una 
pantalla de confirmación. 
La pantalla debe mostrar el siguiente mensaje: 
“¿Está seguro que desea eliminar este agente y todas sus propiedades?” 
Debajo del mensaje deben existir dos botones: 
Botón 
Descripción 
Cancelar 
Cancela la eliminación y devuelve al administrador 
al listado de agentes. 
Aceptar 
Confirma la eliminación del agente seleccionado. 
Si el administrador presiona Cancelar, el sistema debe regresar al listado de 
agentes sin realizar ningún cambio. 
Si el administrador presiona Aceptar, el sistema debe eliminar el agente 
seleccionado y las propiedades asociadas a dicho agente. Luego debe redirigir al 
administrador al listado de agentes. 
Consideraciones al eliminar un agente 
Al eliminar un agente, el sistema debe tomar en cuenta la información relacionada 
con sus propiedades. 
La eliminación del agente debe incluir o gestionar correctamente los siguientes 
datos asociados: 
●​ Propiedades registradas por el agente. 
●​ Imágenes de las propiedades. 
●​ Mejoras asociadas a las propiedades. 
●​ Ofertas realizadas sobre las propiedades del agente. 
 
●​ Conversaciones o mensajes relacionados con las propiedades del agente. 
●​ Propiedades favoritas de clientes relacionadas con las propiedades del 
agente. 
Si el agente tiene propiedades vendidas, el sistema también debe eliminar o 
gestionar correctamente los datos relacionados para evitar registros huérfanos o 
inconsistencias en la base de datos. 
Validaciones para eliminar agente 
Antes de eliminar un agente, el sistema debe cumplir las siguientes validaciones: 
●​ El usuario autenticado debe tener rol Administrador. 
●​ El agente seleccionado debe existir. 
●​ El usuario seleccionado debe tener rol Agente. 
●​ El sistema debe confirmar la acción antes de ejecutar la eliminación. 
●​ La eliminación debe ejecutarse de forma completa, incluyendo las 
propiedades y datos relacionados, para evitar inconsistencias. 
Si el agente no existe, el sistema debe mostrar un mensaje como: 
“El agente seleccionado no existe.” 
Si ocurre un error durante la eliminación, el sistema debe mostrar un mensaje como: 
“No fue posible eliminar el agente. Intente nuevamente más tarde.” 
Si el agente se elimina correctamente, el sistema debe mostrar un mensaje como: 
“El agente fue eliminado correctamente.”

Al eliminar una mejora, el sistema debe gestionar correctamente la relación entre la 
mejora y las propiedades asociadas.

●​ Se debe eliminar la mejora seleccionada. 
●​ Se deben eliminar las asociaciones entre la mejora y las propiedades que la 
tenían asignada. 
●​ No se deben eliminar las propiedades asociadas. 
●​ No se deben eliminar las imágenes, ofertas, favoritos ni conversaciones de 
las propiedades asociadas. 
●​ Si una propiedad queda sin mejoras luego de eliminar una mejora, la 
propiedad debe mantenerse registrada en el sistema.

●​ La mejora seleccionada debe existir. 
●​ El sistema debe solicitar confirmación antes de ejecutar la eliminación. 
●​ Si la mejora está asociada a propiedades, el sistema debe remover 
correctamente dichas asociaciones. 
Si la mejora seleccionada no existe, el sistema debe mostrar un mensaje como: 
“La mejora seleccionada no existe.” 
Si ocurre un error durante la eliminación, el sistema debe mostrar un mensaje como: 
“No fue posible eliminar la mejora. Intente nuevamente más tarde.” 
Si la mejora se elimina correctamente, el sistema debe mostrar un mensaje como: 
“La mejora fue eliminada correctamente.”

Mensaje sugerido: 
“No está autorizado para acceder a este recurso.”

Persistencia de Datos 
●​ Se debe utilizar Entity Framework Core con el enfoque Code First para la 
gestión y persistencia de datos. 
Interfaz de Usuario 
●​ El proyecto debe contar con una interfaz intuitiva y visualmente clara, 
utilizando Bootstrap como framework de diseño o cualquier otro framework 
de css. 
Arquitectura 
●​ El proyecto debe implementar Onion Architecture, aplicada de manera 
correcta y consistente al 100%.​
 
●​ Cualquier error en su aplicación será considerado como una implementación 
incorrecta. 
Repositorios y Servicios 
●​ Se deben crear repositorios genéricos y servicios genéricos para la gestión 
de datos.​
 
●​ Los servicios deben ser utilizados por los controladores de la WebApp. 
Autenticación y Seguridad 
●​ Se debe implementar ASP.NET Identity para el manejo de usuarios y roles.​
 
●​ La API debe estar protegida mediante JWT (JSON Web Tokens).​
 
 
●​ Si un usuario de tipo desarrollador intenta iniciar sesión en la WebApp, se le 
debe notificar que no tiene permisos para acceder.​
 
●​ Si un usuario de tipo cliente o agente intenta iniciar sesión en la Web API, se 
le debe indicar que no tiene permisos para acceder. 
Mapeo de Datos 
●​ Se debe utilizar AutoMapper para el mapeo entre ViewModels, Entities y 
DTOs. 
Documentación de la API 
●​ La API debe documentarse utilizando Swagger y sus herramientas de 
generación de documentación. 
Requisitos Funcionales Específicos 
●​ Todos los precios de las propiedades deben estar expresados en pesos 
dominicanos (DOP).​
 
●​ Todas las pantallas que listan propiedades deben incluir los mismos filtros 
definidos en la sección Home del documento.
